## Actions taken

1. **VM created** — name `DC01`, resource group `rg-adlab`, region **Belgium Central** (chosen
   over the lab's default suggestion of Brazil South — operator is based in Luxembourg, better
   RDP latency).
2. **Size:** `Standard_B2as_v2` (2 vCPU, 8 GiB RAM, AMD) — the plain `B2s` (Intel, 4 GiB) was not
   available/visible in this region's size picker at the time of creation; the v2 AMD variant is
   functionally equivalent for AD DS and was the cheapest available option (~$0.096/hour).
3. **Image:** Windows Server 2022 Datacenter: Azure Edition — Gen2.
4. **Security type:** Trusted launch (Secure Boot + vTPM enabled, no extra cost).
5. **OS disk:** Standard SSD LRS (switched from the Premium SSD default — no performance need
   for this workload, saves roughly half the monthly disk cost).
6. **Networking:**
   - New virtual network `DC01-vnet`, subnet `default (10.0.0.0/24)` — **note this name**,
     `CLIENT01` must join this same virtual network later, not a new one.
   - New public IP `DC01-ip`, Standard SKU, static assignment.
   - New NSG `DC01-nsg` with a single inbound rule restricting RDP (3389/TCP) to the operator's
     home public IP in `/32` notation (rule name `Allow-RDP-MyIP`, priority 1010). The IP address
     itself is intentionally not recorded here — see the redaction rule in
     [`journal/README.md`](../README.md).
     - Note: the in-wizard NSG rule editor collided repeatedly on priority 1000 (a leftover
       `default-allow-rdp` rule open to `Any`, from before switching from Basic to Advanced NSG
       mode) even after attempting to edit/delete it. Using priority `1010` for the new rule
       resolved it cleanly.
   - Auto-shutdown: **not available** in Belgium Central (the `Microsoft.DevTestLab` feature is
     not yet offered in this region). Falling back to manual deallocate discipline, per
     [`COST-CONTROL.md`](../../COST-CONTROL.md).
7. **Management/monitoring choices:** Defender for Cloud Basic plan enabled (free); managed
   identity, Entra ID login, backup, Site Recovery, and guest diagnostics all left disabled —
   none apply to a domain controller build. Boot diagnostics enabled (nominal cost, useful
   safety net for viewing the console if RDP becomes unreachable during promotion).
8. **Private IP set to static** (`10.0.0.4`), via the NIC's IP configuration — prevents the
   address from changing and breaking DNS once client machines depend on it.
9. **Connected via RDP** from the operator's real machine to the VM's public IP, as `labadmin`.
10. **Installed the AD DS role** (Server Manager → Add Roles and Features → role-based
    installation → Active Directory Domain Services).
11. **Promoted the server to a domain controller** — new forest:
    - Root domain: `corp.adlab.local`, NetBIOS `CORP`
    - Forest and domain functional level: Windows Server 2016
    - Global catalog: Yes · DNS Server: Yes · Create DNS Delegation: **No** (expected and correct
      — there is no parent zone to delegate from for a new, isolated lab forest; the warning
      Windows shows here is standard for a first-forest promotion, not an error)
    - Database, log, and SYSVOL folders left at the default `C:\Windows\...` paths — acceptable
      for this lab's scale; production deployments typically place these on separate dedicated
      disks for I/O isolation and performance.
    - DSRM password set and recorded in the operator's password manager (distinct from the
      `labadmin` password).
    - Installation confirmed, server restarting.

## Validation

Ran post-restart, logged in as `CORP\labadmin`. All three confirm the forest is healthy and
match the simulator's lesson from ticket
[2026-07-16_01](../../../iam_guide/lab-journal/tickets/2026-07-16_01_console-tour-domain-facts.md)
— now on a real directory instead of a fictional one.

**`Get-ADDomain`** — domain-level facts and the three domain-level FSMO roles:
```
DNSRoot               : corp.adlab.local
NetBIOSName           : CORP
DomainMode            : Windows2016Domain
DomainSID             : S-1-5-21-4232253284-1205498955-2197313283
PDCEmulator           : DC01.corp.adlab.local
RIDMaster             : DC01.corp.adlab.local
InfrastructureMaster  : DC01.corp.adlab.local
DomainControllersContainer : OU=Domain Controllers,DC=corp,DC=adlab,DC=local
```

**`Get-ADForest`** — the two forest-level FSMO roles `Get-ADDomain` cannot show:
```
ForestMode          : Windows2016Forest
DomainNamingMaster  : DC01.corp.adlab.local
SchemaMaster        : DC01.corp.adlab.local
GlobalCatalogs      : {DC01.corp.adlab.local}
Domains             : {corp.adlab.local}
```

**`Get-ADDomainController`** — confirms DC01 itself:
```
IsGlobalCatalog   : True
IPv4Address       : 10.0.0.4
ComputerObjectDN  : CN=DC01,OU=Domain Controllers,DC=corp,DC=adlab,DC=local
OperatingSystem   : Windows Server 2022 Datacenter Azure Edition
OperationMasterRoles : {SchemaMaster, DomainNamingMaster, PDCEmulator, RIDMaster...}
```

All five FSMO roles sit on DC01, as expected for the only DC in a brand-new forest — three from
`Get-ADDomain`, two from `Get-ADForest`, exactly the split learned in the simulator.
`ComputerObjectDN` confirms `Domain Controllers` is a real **OU** (`OU=Domain Controllers`), not
a container — the A1 finding, now verified against a real directory rather than a fictional one.

DNS: the promotion (`-InstallDNS` / "DNS Server: Yes") automatically pointed DC01's own network
interface at `127.0.0.1` — confirmed via `Get-DnsClientServerAddress`. No manual step was needed.
The virtual network's DNS setting (pointing future VMs at `10.0.0.4`) is deferred to when
`CLIENT01` is created, since it has no effect on DC01 itself.
